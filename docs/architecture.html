Orientation

System at a glance

A browser talks to one API route. That route runs the agent, saves the result, and returns both the answer and a summary of how it was reached.

Three external services are involved, and the app degrades rather than fails when any of them is absent. Without a database it answers but remembers nothing. Without Langfuse keys it answers and records runs locally but sends no traces. Only the model is genuinely required.

The shape of a request

The request lifecycle

Five stages, always in this order. Each one opens a trace span, so the picture below and the timeline on a run page are the same thing.

The number of model calls per question is not fixed. A question caught by a routing rule and sent to the terminal refusal branch skips both the router's model call and the planner entirely, so it costs one call. An ordinary question the rules do not catch costs three.

Stage 1

Router

Decides which subgraph handles the question, before any work is done. lib/agent/router.ts

The router asks the model, but it does not trust it. Three things happen in order, and the earliest one to produce an answer wins.

The nine rules, in order

Order matters: the first rule that matches wins, so the most serious categories are checked first.

RuleFires onSends to
other-bankBarclays, HSBC, Monzo, Starling …refusal
creative-writing“write me a poem / song / story”refusal
investment-advice“should I invest / put it in stocks”refusal
legal-adviceSection 75, chargeback, ombudsmanrefusal
account-specific“my balance”, “am I overdrawn”escalation
fee-waiver“waive the fee”, “just this once”escalation
complaint-or-disputecomplaint, bereavement, close my accountescalation
active-fraudscam, phishing, “safe account”, stolenfraud
calculation“how much would … overdraft / limit”accounts

Why rules at all, when there is a perfectly good model? Because the cost of being wrong is not symmetrical. Routing a fee question to the wrong branch produces a clumsy answer; routing “what is my balance” to a branch that answers it produces an invented number in a banking app. A regex cannot be charmed, and it costs nothing to run.

If the model call fails outright, the router falls back to escalation when the policy tool objected and knowledge otherwise — the safe default, because the knowledge composer refuses to invent anything.

Stage 2

Planner

Writes the whole list of tool calls before any of them run. lib/agent/planner.ts

The planner is given only the tools its branch is allowed to use, and returns JSON: a one-sentence rationale and up to four steps, each with an intent, a tool name and arguments. Planning up front rather than improvising one call at a time means the whole plan is visible in the trace and can be judged on its own. 

{
  "reasoning": "Look up the published fee, then confirm the cap.",
  "steps": [
    { "intent": "Find the passage about overdraft fees",
      "tool": "search_knowledge_base",
      "args": { "query": "unarranged overdraft fee" } },
    { "intent": "Confirm the exact published figure",
      "tool": "lookup_fee",
      "args": { "fee": "unarranged_overdraft" } }
  ]
}

Everything the model returns is checked

validatePlan() is the reason a hallucinated tool name never reaches the executor. It drops any step that names a tool which does not exist, or one the branch is not permitted to use, renumbers the survivors, and records what it dropped in the trace.

MAX_STEPS = 4
A hard ceiling. More steps means more latency and more chances to go wrong, and nothing in this domain needs five lookups.
Unknown tool
Dropped, with the name recorded. The run continues with whatever remains.
Wrong branch
Dropped. create_handoff planned on the knowledge branch never runs.
No usable steps
Falls back to searching the knowledge base, which is always a defensible first move.
Terminal branch
refusal returns an empty plan without calling the model at all.
Stage 3

Executor

Runs the plan, one tool at a time, each in its own span. lib/agent/executor.ts

A failing tool does not stop the run. The failure is recorded and the next step goes ahead, because a partial set of facts still beats no answer, and the composer is told plainly which steps failed.

Missing arguments are filled in

Models routinely forget the obvious argument — most often the search query itself. Rather than failing the step, withDefaults() supplies the question:

ToolMissing argumentFilled with
search_knowledge_basequerythe customer's question
check_request_permittedrequestthe customer's question
assess_fraud_riskdescriptionthe customer's question
create_handoffsummary, reason, urgencythe question, a generic reason, routine

Afterwards the executor collects every distinct citations entry returned by any step. That deduplicated list is what appears under the answer as its sources.

Stage 4

Composer

Turns the tool results into the sentences a customer reads. lib/agent/composer.ts

The composer receives the tool results and nothing else — no conversation history, no general knowledge licence. Its prompt is assembled from three parts: a fixed house style, the branch's own guidance, and the formatted results.

House style
British English, two to five sentences, no greeting, no headings or bullets. Amounts written as the source writes them — “6 pounds per day”, not “£6/day”.
Phone numbers
Only two exist: 0800 555 0199 for lost cards and 0800 555 0177 for fraud. The general line has no published number, so it is named and given hours, never a number.
Branch guidance
Each subgraph adds its own instruction — the fraud branch leads with the action and the number; the accounts branch states the tool's figure and shows no workings.
maxTokens 1500
Generous on purpose. A reasoning model spends tokens thinking before it writes; too small a budget produces an empty reply rather than an error.

A real failure this instruction fixed. The house style originally said “give the phone number whenever the answer involves calling someone”. The fact sheet publishes the general line's hours but no number — so the model invented one. The guardrail caught it and blocked the answer, which is the system working, but the instruction was the actual bug.

Stage 5

Guardrail

Assumes everything upstream got it wrong, and looks for the specific ways a bank assistant causes harm. lib/agent/guardrail.ts

The guardrail is plain code, not another model call. A model asked to check a model is only as reliable as the thing it is checking, and it fails in exactly the situations where you need it most.

Repair runs before any check

The first thing that happens is normalisation, and it is load-bearing. Models write can’t with a typographic apostrophe and one‑time with a non-breaking hyphen. Both look identical on screen and both defeat a plain-text check, so every check after this point would silently miss them.

RepairExample
Typographic punctuation → plaincurly quotes, non-breaking hyphens, ellipsis
Currency symbol → the word£6 becomes 6 pounds
Strip emphasis**6 pounds** becomes 6 pounds
Strip list and heading markersleading -, *, ##

The seven checks

Four are blocking: failing one replaces the answer entirely. Three are advisory: they are recorded on the run page but the answer still goes out.

CheckCatchesEffect
no invented balanceA money amount stated as the customer's balanceblocks
no unauthorised promise“I have waived…”, “I have raised your limit”blocks
phone numbers are realAny number that is not one of Meridian's twoblocks
answer is substantialUnder 15 charactersblocks
figures are sourcedA figure not present in any tool resultwarns
refusal is a refusalAn out-of-scope branch that answered anywaywarns
no internal language“according to my knowledge base”warns

figures are sourced is deliberately advisory. Ordinary sentences contain ordinary numbers, and blocking on that would break far more than it fixes.

A block chooses its replacement

The replacement has to fit the question it replaces. Telling someone asking about another bank that you cannot see their account reads as though the assistant misunderstood.

refusal branch
“I can only answer questions about Meridian Bank's own published services…”
balance question
“I have no access to customer accounts, so I cannot see your balance…”
anything else
The general refusal, with the phone line and its hours.

Branching

The five subgraphs

A subgraph is a branch with its own tools and its own house style. Routing to one early keeps each branch small.

The fraud branch never has to think about exchange rates; the refusal branch never runs a tool at all. Restricting the tool list per branch is also a safety mechanism, not just tidiness — it is why the planner cannot arrange a handoff on a general knowledge question, or reach for a calculator on a question that should be declined.

SubgraphHandlesToolsComposer is told
knowledge General questions about published products, fees, hours and the app. The default. 10 Answer only from retrieved passages; quote figures exactly.
accounts Anything needing a calculation or a limit checked. 8 Give the tool's figure, never your own. Show no workings.
fraud Scam calls, suspected fraud, anyone who may be at risk now. 5 Lead with the action and the number. Be brief and calm.
escalation Complaints, disputes, bereavement, anything account-specific. 5 Say what you cannot do in one sentence, then give the reference and route.
refusal Other banks, financial or legal advice, off-topic requests. Terminal. 0 Decline in one or two sentences. Do not answer any part of it.

Terminal means the pipeline short-circuits. On the refusal branch the planner is skipped entirely and the executor has nothing to run, so the composer writes from an empty result set. That is the point: there is nothing to look up, and the only correct answer is a decline.

Mechanism

How tool calling works

Every tool is a plain TypeScript object with a description, typed parameters, a list of branches allowed to use it, and a function. lib/agent/tools.ts 

type Tool = {
  name: string;
  description: string;         // the model reads this to choose
  parameters: ToolParameter[]; // name, type, required, optional enum
  subgraphs: SubgraphName[];   // which branches may call it
  mutates: boolean;            // true when it writes something
  run: (args) => ToolResult | Promise<ToolResult>;
};

type ToolResult = {
  ok: boolean;                 // false is an expected outcome, not a crash
  summary: string;             // what the composer actually reads
  data?: Record<string, unknown>;
  citations?: string[];        // where the answer came from
};

That one definition is used three ways, which is why a tool is described in exactly one place and can never drift out of sync with itself:

describeTools()
Renders the catalogue as text for the planner's prompt, so the model sees only the tools its branch may use.
toolSchemas()
Converts to OpenAI-style JSON function schemas, the format Groq accepts for native tool calling.
/tools page
Reduced to plain data on the server and rendered as a form, so any tool can be run by hand.

Every tool is deterministic and offline

Not one of them calls a third-party API. Given the same arguments, each returns the same result forever. That is a deliberate constraint with three payoffs: a run can be replayed, a test can assert on exact figures, and a wrong answer can always be traced to either the tool or the model that called it — never to a service having a bad day.

The corollary is that ok: false is an ordinary outcome, not an exception. A tool throws only for a genuine bug; a tool that cannot do what was asked says so and the run carries on.

Self-correcting retrieval

search_knowledge_base takes an optional category filter, which the planner guesses. A wrong guess used to hide the very document that answered the question — a lost-card question filtered to fraud returned nothing, because lost cards live under cards. The tool now retries without the filter whenever a filtered search comes back empty, and records that it widened. Narrowing can never do worse than not narrowing.

Retrieval

Knowledge and retrieval

Eleven documents in a TypeScript array, searched with BM25 in the same process. lib/knowledge/

There is no embedding model and no vector database. For a fact sheet of this size that is not a compromise: the vocabulary is small and customers use the same words as the documents, which is exactly where BM25 is strongest. It is also instant, free, and returns identical scores every time — which is what makes it testable.

What happens to a query

tokenise
Lower-cased, split on words and figures. Figures keep their commas, so 25,000 survives as one token — it is the answer to a question.
stop words
About 60 words carrying no signal are dropped.
stem
Crude suffix stripping so cards matches card. Plurals lose only the s, so charges becomes charge, not charg.
score
BM25 with the standard k1 = 1.5, b = 0.75. Repeated words stop adding value; rare words count for far more than common ones.
threshold
Below 0.35 a hit is dropped as noise. Returning nothing is what lets the agent say it does not have that information, instead of answering from whatever scored least badly.

The fact sheet is imported, never copied. The single source of truth is BANK_FACTS in config.ts; the knowledge base imports it as one document and adds ten more alongside. There is exactly one place a fact can be wrong.

The /knowledge page runs this same search and shows the same scores, so when an answer is thin you can see immediately whether the passage was missing or merely unfindable.

Observability

Tracing

Every stage opens a span. At the end of the request they are posted to Langfuse as OpenTelemetry, in one awaited batch. lib/trace.ts, lib/langfuse.ts

Why OpenTelemetry and not Langfuse's own ingestion API

Organisations created from September 2026 onwards cannot use the older v3 ingestion endpoint. It still answers 207 Accepted to every request and then stores nothing — the worst possible failure mode, because everything looks healthy.

This was caught only by posting a run and then reading it back. The observations API returned an empty list. OTLP is the supported route and, being a standard, is what any other tracing backend would also accept.

Identifiers
Real OpenTelemetry hex: 16 bytes for a trace, 8 for a span. Anything else is rejected outright, so a malformed id is caught before sending rather than at the collector, which refuses the whole batch without saying which span was at fault.
One root span
OTel has no separate trace object to hang a name on. Without a root, the stages arrive as unrelated top-level spans.
Error propagation
An error in any stage colours the root red, so a failed run cannot look green in the list and go uninvestigated.
Awaited, not fire-and-forget
On serverless the function can freeze the moment the response is returned. Anything still in flight would simply vanish.
Both variable names
Langfuse's Python SDK reads LANGFUSE_HOST, the JavaScript one LANGFUSE_BASE_URL. Both are accepted, because a key set under the other spelling is indistinguishable from one never set.

The same spans are returned to the browser and stored, so the timeline on a run page is identical whether or not Langfuse is switched on. Tracing is an optional mirror, never the only record.

Persistence

What gets stored

Three tables in Neon Postgres, over the HTTP driver. Every row is labelled with STUDENT_NAME. lib/db.ts

TableOne row perNotable columns
messagesMessage, user and assistant alikesession_id, role, content
runsQuestion answeredsubgraph, guardrail_verdict, tools_used, trace_id, total_ms, detail (JSONB)
handoffsHandover to a personreference, urgency, summary

The detail column holds the whole run as JSON — plan, every tool call with its arguments and result, the guardrail report, and the timeline. That is what lets a run page rebuild a run exactly, weeks later, without Langfuse.

ensureTable() runs on every chat request and every statement in it is idempotent: CREATE TABLE IF NOT EXISTS, then ALTER TABLE … ADD COLUMN IF NOT EXISTS, then CREATE INDEX IF NOT EXISTS. Running it against a database that already has everything changes nothing.

Rationale

Decisions worth knowing

Each of these was a fork in the road, and each was taken for a reason that outlives the code.

Plain fetch, no SDK
Groq speaks the OpenAI dialect, so the whole call is one readable HTTP request. You can see exactly what leaves the server, and there is no client library to go stale.
Guardrail in code
A model checking a model shares its blind spots. Code cannot be charmed by a persuasive draft, and it runs in microseconds.
Rules before the model
The cost of misrouting is asymmetric. The dangerous categories are cheap to match with a regex and expensive to get wrong.
Deterministic tools
Reproducible runs, assertable tests, and a clean split between a broken tool and a model that called a working one badly.
BM25, not embeddings
Small vocabulary, shared wording, instant, free, and identical every time. A vector store would add a service and remove the ability to test exact scores.
Plan up front
The whole plan can be judged on its own, and a hallucinated tool name is dropped before anything runs.
Per-branch tool lists
A safety boundary, not tidiness. The planner physically cannot reach a tool its branch is not allowed.
Trace stored twice
Langfuse is a mirror. The run page works from Postgres alone, so observability never becomes a dependency.
